# Releasing and install channels

`specbutler` uses tagged source releases on GitHub; it is not published
to PyPI.

## Channels

- **Stable:** an annotated `vX.Y.Z` tag with a matching GitHub Release. Install
  the VCS requirement at that immutable tag. `spec update` checks published
  GitHub Releases and advances tagged installs to the newest non-prerelease
  version.
- **Development:** an explicit VCS requirement at `@main`, or an editable
  checkout. This channel can change after every merge and is not a release.

Install the CLI with pipx so its dependencies do not mutate a project or system
Python environment. Project dependencies remain per-worktree concerns; the
Python configuration generated by `spec init` creates `.venv` in each
worktree and points its detected Python verify gates at that environment.

`spec update` deliberately treats the two channels differently. It advances an
immutable version-tag install to the newest non-prerelease version tag. An
`@main` install must be refreshed by rerunning its `pipx install --force`
command, and an editable checkout is updated with normal Git and
package-development commands.

## Automated release flow

After required CI passes on `main`, `.github/workflows/version.yml` opens an
automated patch-version PR. Once that version bump reaches `main`, the workflow
creates the matching annotated tag and an idempotent GitHub Release with
generated notes. A release is complete only when all three agree:

1. `pyproject.toml` reports `X.Y.Z`.
2. Tag `vX.Y.Z` points at that version commit.
3. GitHub Release `vX.Y.Z` exists.

The bump job is dormant in a new repository until release credentials are
configured. Create a dedicated fine-grained PAT or GitHub App token that can
push `release/*` branches and open pull requests, store it as the repository
secret `VERSION_BUMP_TOKEN`, and only then enable the workflow:

```bash
gh variable set SPEC_BUTLER_AUTOMATED_RELEASES \
  --repo specbutler/specbutler \
  --body true
```

Do not reuse a broad personal login token for this secret. This repository's
bootstrap releases already exist; do not recreate or move an existing tag.
Once automation is enabled, the version workflow owns the next version PR,
tag, and GitHub Release.

The generated container worker installs the tag matching the host package
version. `spec container smoke` rejects a version mismatch and, when host
provenance includes a Git commit, a source-commit mismatch. A moving `main` or
editable build may therefore need a custom worker built from that exact source;
do not present such a build as a tagged release.

Before changing repository visibility, verify the full test, lint, package,
dependency-audit, and secret-scan jobs, and smoke the installed CLI from the
built wheel. Review the repository history and tracked specs for information
you do not intend to disclose.

Once the repository is public and the matching GitHub Release exists—but before
announcing it—run `gh release view vX.Y.Z`, exercise the stable pipx install,
and smoke the generated container worker. The generated worker fetches the
tagged `spec` source over public HTTPS, so that baseline is not a reliable
pre-visibility check. Legacy tags without a GitHub Release do not satisfy the
stable-channel contract above.

After the repository is public, also enable and verify GitHub private
vulnerability reporting so the primary path in [SECURITY.md](SECURITY.md) is
available; the documented email address remains the fallback.
